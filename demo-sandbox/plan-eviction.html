Sliding-Window TTL — Eviction Approaches

Repo: CSharpCache · Baseline: TtlCache<TValue> with 1/3-threshold lazy refresh in TryGet

Recommended Alternative
Eager Update on Every Read
★ Recommended
Remove the 1/3 guard; call TryUpdate on every hit where SlidingWindowTicks > 0, capping at AbsoluteCapTicks.
Pros
  • True sliding-window semantics — deadline resets on every access
  • Minimal delta from existing code
  • No new data structures or threads
  • CAS failure is safe: other thread set the same deadline
Cons
  • Extra CAS write on every hot-path read
  • Contention cost grows with concurrency on the same key

Configurable Refresh Threshold
Promote the hardcoded 1/3 to a constructor parameter refreshFraction (0–1); expose it via CacheEntryOptions per-entry.
Pros
  • Zero new code paths — purely parametric
  • Backward-compatible default (keep 1/3)
  • Callers can tune per-key (0 = always refresh)
Cons
  • Still approximate — not a true sliding window
  • Adds surface area to CacheEntryOptions
  • Correct value is workload-dependent; easy to misuse

Parallel Last-Access Dictionary
Keep a second ConcurrentDictionary<string, long> for last-access timestamps; TryGet updates only that dictionary, and SweepExpiredEntries computes effective deadlines at eviction time.
Pros
  • No struct replacement in the hot path — one atomic long write
  • Sweep is the single source of eviction truth
  • Easy to snapshot last-access for observability
Cons
  • Two dictionaries must stay in sync (remove from both)
  • Sweep logic grows more complex
  • Extra memory per entry; two lookups in sweep

Mutable Class Entry + Volatile Deadline
Convert CacheItem<TValue> from a readonly struct to a class; declare DeadlineTicks as volatile long; TryGet updates it with Interlocked.Exchange — no CAS retry loop.
Pros
  • Eliminates CAS retry contention entirely
  • Single atomic write — simplest concurrency model
  • No dictionary replacement; same key stays in place
Cons
  • Heap allocation per entry — GC pressure on large caches
  • Struct → class change breaks the existing immutability guarantee
  • Requires reasoning about torn reads on 32-bit targets

Channel-based Async Refresh
TryGet posts (key, newDeadline) to a bounded Channel<T>; a single background Task drains the channel and applies TryUpdate — zero contention on the read hot path.
Pros
  • Hot read path is write-free — highest read throughput
  • Can batch updates and coalesce duplicate keys
  • Natural backpressure via bounded channel capacity
Cons
  • Eventual consistency — entry may expire before update applies
  • Dropped events when channel is full under burst load
  • Task lifecycle + CancellationToken wiring adds complexity

Min-Heap Priority Queue Sweep
Replace the O(n) timer sweep with a PriorityQueue<string, long> ordered by next deadline; Set/TryGet enqueue updated entries; sweep dequeues only entries whose deadline has passed using lazy deletion.
Pros
  • O(log n) sweep — avoids full-scan cost on large caches
  • Sweep interval can be dynamically adjusted to next expiry
  • Efficient for sparse or long-TTL workloads
Cons
  • PriorityQueue is not thread-safe — requires a dedicated lock
  • No native key-update support → lazy deletion adds stale entries
  • Significant refactor touching sweep, Set, and TryGet paths
