03 —Questions for the Author
ownership 01
Who is meant to own the cache lifetime?
Runner.RunAsync disposes a cache it received as a parameter — the caller has no opportunity to ensure cleanup if the method throws before its finally. Is this intentional? If so, the contract should be documented in XML docs ("takes ownership of cache; callee disposes"). If not, flipping to await using var cache = CreateCache(config); in Program.cs with no disposal inside Runner is the safer, idiomatic fix.
→ Program.cs:22–23 · Runner.cs:38
correctness 02
What should happen when the monitoring loop throws?
Currently an exception in the while loop leaves workers running against a disposed cache. Should they be hard-cancelled immediately (fastest shutdown), allowed to drain their current operation (safest for metrics accuracy), or does the timeout-based CancellationTokenSource serve as the only intended safety net? The answer shapes whether a catch { cts.Cancel(); await Task.WhenAll(workers); throw; } is the right fix or something more graceful.
→ Runner.cs:24–32
intent 03
Is sharing one byte[] value across all workers intentional?
Every worker calls cache.Set(key, value, …) with the same reference — the array allocated on line 7. Concurrent reads of the array contents are safe, but all cache entries point to the same backing object. If a future test mutates the value between sets, results will be silently corrupted. If this is a deliberate allocation-avoidance optimisation for the benchmark, a comment would make that explicit and safe for future maintainers.
→ Runner.cs:7, 19
edge case 04
What is the intended behaviour when HotsetFraction = 0?
When HotsetFraction is zero, _hotCount = 0. Then random.Next(0) always returns 0 (a well-defined .NET behaviour), and random.Next(0, _keySpace) samples the entire key space — effectively uniform. Is this the desired degenerate case? A guard and a meaningful exception or log message would make the boundary explicit: if (_hotCount == 0) throw new ArgumentException("HotsetFraction too small");
→ KeySampler.cs:11, 18–19
reproducibility 05
Is deterministic replay a goal, and is the seed being recorded?
config.Seed ?? Environment.TickCount suggests reproducibility is at least considered. But the seed is never printed, so a benchmark run that produces an interesting result can't be re-run identically. If replay is a goal, log the effective seed at startup. If it isn't, Random.Shared (.NET 6+) is thread-safe and removes the seeding ceremony and the sequential-seed dance in the worker Select entirely.
→ Runner.cs:8, 13
