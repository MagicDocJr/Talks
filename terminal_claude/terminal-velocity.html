Flags explained: -W = writable (lets you type, not just view). -p 7681 = port. By default ttyd is read-only, without -W the audience would see nothing happen when you type.

Demo script (under 4 min):

  1. zellij: split a pane (Ctrl+P → R), switch tabs. Point at the keybind hints in the status bar.
  2. zsh + starship: partial command, show ghost suggestion. Note the prompt segments.
  3. zoxide: z rik, then zi.
  4. yazi: y, browse, preview, quit.
  5. rg + fzf: rg "ICustomerRepo" | fzf.
  6. helix: open a file, show selection-first edit.
  7. claude: claude, ask "which .csproj files reference Serilog?". Let it run rg internally. Stop there, the next slides cover Claude properly.

Sandbox-dir tip: drop a small real .NET repo into ~/talks/demo-sandbox so the demo has something believable to grep through. Avoid your actual work tree, you don't want stray git state showing on the projector.

If the iframe is blank: ttyd isn't running. The slide shows setup instructions. Worst case, alt-tab to Windows Terminal, the deck still works.

02 · output-format

02.Ask Claude for HTML, not markdown.

Default fra LLMs er markdown. HTML er en superkraft når Claude skriver fila rett til disk.

› Make me an HTML cheatsheet of CSharpCache's public API. Scan the repo. Produce ./api-cheatsheet.html, one self-contained file. Include: a table of every public type/method, signature, one-line summary, link to file:line. Add a tiny "common usage" snippet at the top.
åpne api-cheatsheet.html ↗

Most important slide in the deck.

Anthropic posted a blog last month titled "The Unreasonable Effectiveness of HTML". The pitch is annoyingly simple:

When you ask Claude for a plan, a comparison, a report, ask for HTML, not markdown. A self-contained .html you open in the browser.

What you get:

  • Tables with color and styling
  • SVG diagrams where needed
  • Buttons and sliders, interactive tuning
  • Copy buttons that dump results back as prompt

What it actually gives you: you read it. Markdown specs go unread. A well-formatted HTML page with the right density engages.

Demo opener: live-run the API cheatsheet prompt against CSharpCache in the ttyd terminal. Once the file's open, the audience gets why for free, five seconds of comparing a markdown table vs. this is enough.

The next 5 slides each show one specific pattern. Each has a prompt you can copy verbatim.

03 · plan & spec

03.Six different solutions, side by side.

6 tilnærminger side-by-side. Trade-offs synlige med ett blikk, ikke begravd i én lang markdown.

› Look at the cache eviction logic in this repo. Generate 6 distinctly different approaches for adding a sliding-window TTL on top of what's there. Output: ./plan-eviction.html, single file, 3×2 grid. Each cell: name, one-line approach, pros, cons, complexity score 1–5, files it would touch. Mark your recommendation in amber.
åpne plan-eviction.html ↗

Use case 1: Planning with HTML.

Classic markdown plan: bullets under headers, linear read. You can't see options 3 and 5 at the same time.

HTML version: a 3×2 grid. One glance tells you "B and D are real candidates". No scrolling.

Generic prompt template:

"Generate N distinctly different approaches to [problem]. Output as ./plan.html with a 3×2 grid. Each cell: name, approach, pros, cons, complexity score, files touched. Mark your recommendation."

Open the HTML next to the terminal. Read, give feedback, ask for "expand approach B into its own plan-B.html". You end up with a small web of interlinked HTML specs: not one linear doc.

Demo: paste the prompt against CSharpCache. Should produce something in ~20 seconds.

04 · code review

04.Code review as annotated HTML diff.

Faktisk diff inline med margin-notater og severity-farger. Send HTML-en til en reviewer.

› Run git log --oneline -15 on this repo. Pick one non-trivial commit (touches >1 file, not a rename or version bump). Produce ./review.html that: 1) renders the actual git diff inline 2) color-codes findings by severity (high/med/low/nice) 3) margin annotations with rationale, not just what 4) file:line refs for anything you flag 5) a "questions for the author" section at the end
åpne review.html ↗

Use case 2: Review as artifact.

Normal agent review: a markdown wall. You lose focus by line 5.

HTML review: the diff itself is rendered, with severity-colored annotations in the margin. Scroll, see context, skip the low-priority stuff.

Why it matters: I send this HTML to a colleague who doesn't know the code. They get the full picture (diff, rationale, severity) in one document they actually read.

Generic prompt template:

"Make an HTML artifact for this PR. Render the actual diff inline with margin annotations. Color-code by severity. Include rationale, not just 'this is wrong'. Write to ./review.html."

Advanced: dispatch parallel subagents, one for security, one for correctness, one for test coverage. Each contributes a section. Merge into one HTML.

Demo: point Claude at CSharpCache, let it pick a recent commit. Show the resulting HTML.

05 · interactive tuning

05.Interactive playgrounds in one HTML.

Slidere for hver parameter, live simulering, copy-knapp som dumper config som kode.

› CSharpCache is a caching library. Build me a tuning playground I can use to pick reasonable defaults. Output: ./cache-playground.html, single file. Controls: maxEntries, ttlSeconds, evictionPolicy. Simulate Zipfian access. Plot hit-rate, evictions/sec live. "Copy as C# initializer" button at bottom.
åpne cache-playground.html ↗

Use case 3: Interactive tuning.

Probably my favorite pattern. When I need to land on the "right" number for something (TTL, timeout, retry backoff, threshold). I ask Claude for an interactive HTML.

Old way: edit value, reload, observe, repeat. Slow.

New way: "Make an HTML with sliders for these params. Animate/simulate. Copy button that dumps the final config."

5 minutes later I have a mini-app. Drag sliders 30 seconds, copy the values, paste into the real code. Done.

Other patterns this works for:

  • Retry strategy: sliders for backoff/jitter/max-retries → graph of total wait time distribution
  • Rate-limit tuning: bucket-size + refill-rate → throughput graph
  • Color palette: HSL sliders → preview of components live

Demo: generate the cache-playground.html live in CSharpCache. Drag the sliders, show the hit-rate respond. Copy the C# config.

06 · reports

06.Reports people actually read.

SVG-diagram, annoterte snutter, gotchas-seksjon. Kollegaer leser det faktisk.

› Write an HTML onboarding explainer for someone joining the CSharpCache project tomorrow. Inspect the actual code. Output: ./onboarding.html Sections: elevator pitch, SVG architecture diagram, "read these 3 files first" with file:line refs, annotated snippet of the key method, gotchas, "how to run tests / extend" cheatsheet.
åpne onboarding.html ↗

Use case 5: Reports that get read.

When I ask Claude to dig through a new area ("how does billing work?", "explain our auth flow"), it's tempting to ask for a markdown spec.

In my experience: they don't get read. Not by me, definitely not by colleagues. Too long, too grey.

HTML report with:

  • SVG diagram at top (Claude can draw simple SVG)
  • Code snippets with syntax highlighting
  • "Gotchas" / "do not do this" section, always the most valuable bit
  • Links to actual files

...gets read. Colleagues scroll it in 3 minutes and learn something.

Generic prompt template:

"Write an HTML explainer for [system X]. Include a simple SVG architecture diagram, 2–3 code snippets showing the main flow, a 'gotchas' section with things that have bitten us before. Link to relevant files."

Demo: the onboarding HTML for CSharpCache should be tangible, show it'd actually onboard someone in 5 minutes vs. reading a markdown README in 30.

.claude/skills/ auto-laster compliance, standards, security.

rikstoto-compliance · security

Min faktiske workflow siste måneden, Stalltips RN-appen.

1. Linear MCP. Jeg starter med en ticket-ID. Claude henter selv: issue body, parent-issue, alle kommentarer, status, labels. Den vet hva som er acceptance-criteria før den skriver en linje kode. Stopper "hva mente du egentlig?"-ping-ponget.

2. Figma MCP. Dette er det største skiftet. Tidligere måtte jeg manuelt forklare designet. Nå peker jeg på en Figma-frame, og Claude leser auto-layout, padding, farger, tokens, varianter direkte. Combo med vår Code Connect-oppsett betyr at Claude vet at denne Figma-knappen mapper til vår <Button variant="primary">.

3. ADB + Playwright. Magien. Claude:

  • Bygger appen lokalt
  • Starter Android-emulator
  • Via ADB: adb shell screencap → henter PNG av skjermen
  • Sammenligner mot Figma-frame (visuelt resonement)
  • "Padding er 4px for liten, font-weight er feil" → fikser → tar nytt screenshot
  • Looper til pixel-match

For web-deler bruker den Playwright MCP samme måte. Resultat: jeg får en PR der screenshot ligger ved siden av Figma, og de er identiske.

4. Skills i repo. .claude/skills/ versjonéres med koden. Vi har:

  • rikstoto-compliance: regulatoriske krav fra Lotteritilsynet. Loader auto når Claude rører limit/pause/exclusion-kode.
  • code-standards: Rikstoto-conventions, naming, struktur.
  • security-review: sjekkliste før commit av noe som rører auth, tokens, kundedata.

Skills laster bare ved behov. Beskrivelsen leses alltid, fullt innhold når relevant. Sparer tokens og holder Claude focused.

Konklusjon for talen: dette er ikke fremtiden. Dette er hverdagen min siste måned. Hver del er bare en MCP-server som man installerer.
